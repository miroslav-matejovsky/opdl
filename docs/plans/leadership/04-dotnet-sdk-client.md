# Stage 04: .NET SDK leadership client

**Effort:** Medium. **Complexity:** Medium. **Risk:** Medium.

Depends on stages 02 and 03. This is where the feature becomes usable by a client
service rather than merely correct in the platform.

## The generation constraint

`conformance-tests/api-specifications/dotnet.go:36` runs `kiota generate` with
`--clean-output` against `sdk-dotnet/src/Opdl.Sdk/Client`. The directory is
deleted and rewritten on every `task all`.

Consequences, and they are not negotiable:

- The leadership HTTP operations from stage 02 arrive in `Client/` for free, with
  no hand-written code. That half needs nothing but regeneration.
- The pipe client cannot be generated, because OpenAPI describes HTTP. It must be
  hand-written.
- **Every hand-written file lives outside `Client/`.** A file placed inside it is
  destroyed silently on the next full build.

Proposed layout, keeping the generated and authored halves visibly separate:

```
sdk-dotnet/src/Opdl.Sdk/
  Client/          generated by Kiota, wiped and rewritten, never edited
  Leadership/      hand-written: pipe client, state machine, public surface
```

The `Opdl.Sdk.csproj` today carries exactly one package reference,
`Microsoft.Kiota.Bundle`. Named pipes need nothing beyond the base class library,
so the dependency set should stay as it is.

## Public surface

A client service should not have to understand pipes, snapshots, epochs, or
reconnection. It should be told what it is and when that changes.

The surface is small on purpose:

- The current state, `Active` or `Standby`, readable at any time.
- An event or callback raised on transition, carrying `LeadershipGranted` or
  `LeadershipRevoked` and the epoch.
- A `CancellationToken` on everything, matching the existing SDK convention
  (`sdk-dotnet/README.md:189`).
- Async throughout, and no blocking on async, per the repository's .NET rules.

The epoch is exposed rather than hidden. A service whose side effects need
external ordering has to be able to carry it, which is the entire reason it
exists.

## Behavior the SDK owns so the service does not

This is the value of the stage. Each item is a mistake a service would otherwise
make on its own.

| Behavior | Why the SDK owns it |
| --- | --- |
| Query the local API on start, before any pipe event | The API is authoritative; the pipe is an optimization. |
| Discard messages whose epoch is not greater than the last seen | Makes duplicates and reordering harmless. |
| Reconnect with backoff after a pipe drop | Platform failover drops the pipe routinely. |
| Re-query the API after every reconnect, before trusting a snapshot | A reconnected client's state is unknown, not stale. |
| Surface `Standby` on disconnection rather than the last known state | A service must not stay Active on the strength of a dead channel. |
| Respond to a resync marker by querying the API | Backpressure overflow is expected under load. |

The disconnection rule deserves emphasis because it is counter-intuitive and
because getting it wrong produces exactly the failure this feature prevents. When
the channel is down, the service does not know it is Active, and behaving as
Active on the strength of a stale belief is what creates two Actives.

Whether the SDK should *demote* on disconnect or *report uncertainty* and let the
service decide is a genuine design question. Reporting `Standby` is the safe
default and the right starting point. A service that can tolerate a brief
uncertain window can be given an explicit opt-in later, once there is a real
service asking for it.

## Reconnect and the platform failover window

The pipe drops when the active platform process is replaced, for roughly 130 to
190 ms on the development baseline (`docs/01-architecture.md:367`). Under the rule
above, every local unit of a leadership-managed type reports `Standby` for that
window even when its machine keeps site leadership throughout.

That is a real behavioral cost and it should be measured rather than assumed. It
is a good reason to keep the initial reconnect backoff short, and a good reason
for stage 05 to record the observed window rather than leave it to inference.

## Documentation

`sdk-dotnet/README.md` currently states "Polling the origin is the only
confirmation mechanism; nothing is pushed" (line 128) and "The API has four
operations, and this is all of them" (line 94). Both become false in this stage
and must be updated in the same change.

The README also carries two stale examples recorded in stage 00, an indexed status
route and a `409` for `registration_key_conflict`. Fixing them is unrelated to
this feature and should be a separate small change, not folded in here.

## Work

1. `Leadership/` namespace in `Opdl.Sdk`, outside `Client/`.
2. Pipe client: connect, read message-mode frames, deserialize, reconnect with
   backoff.
3. State machine: snapshot, deltas, epoch filtering, disconnection handling.
4. Public surface: current state, transition events, epoch, cancellation.
5. Composition with the generated client for the authoritative API queries.
6. README rewrite of the pushed-versus-polled sections.

## Tests

- Unit tests over the state machine with a fake channel: snapshot then deltas,
  out-of-order epochs, duplicate epochs, resync marker, disconnection.
- Reconnect backoff is bounded and cancellable.
- The service-visible state is `Standby` while the channel is down.
- E2E through `scenarios`, in stage 05.
