**The headline: the new scenario found a real bug in Stage 5's foundation.**

Olric's create-if-absent is unsafe for a sub-second window right after a member joins, while partitions move. Reproduced standalone: 40 keys written by node A alone, then node B joins — **26 of 40** had `Create` wrongly report the key absent, win, and **permanently overwrite** the value. `Get` stays correct throughout, so the fabric contradicts itself. The adapter is right; Olric is documented AP and consistent only "when the cluster is stable," and a join is exactly when it isn't. The contract suite never caught this because every case runs against one stable member.

That breaks the promise all of registration's idempotency rests on. Visible impact is a duplicate `confirmed` event; the latent one is worse — a conflicting POST in that window could win instead of returning 409, overwriting an accepted claim. Per your call, it's documented in `docs/backlog/fabric.md` with measurements and reproduction, stated in `fabric/doc.go` next to the promise it qualifies, flagged in the README, and the scenario asserts what the platform actually does with the reason in place. The reproduction probe is in the scratchpad, not the repo.
